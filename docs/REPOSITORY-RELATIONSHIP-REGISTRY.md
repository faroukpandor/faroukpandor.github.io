## Relationship rules for every repository

1. Each repository should link to this registry and maintain a short local `docs/PORTFOLIO-RELATIONSHIPS.md` (or a root `PORTFOLIO-RELATIONSHIPS.md` if no docs directory exists) describing its role, canonical repo, upstream/dependent repos, related projects, deployment, data/IP boundary, and one next action.
2. Repositories should **link and reuse contracts**, not duplicate entire applications or silently fork business logic. Any shared package/API/schema requires an explicit dependency, version/compatibility note, and owner.
3. Keep status values separate: IDEA → RESEARCH → EXPERIMENT → PROJECT → DEVELOPING → ACTIVE → COMMERCIAL → ARCHIVED. Do not mark a project live without a verified URL and successful check.
4. Record provenance: original owner, upstream/fork, creator/contributor, licensing, customer/client, data source/license, deployment owner, and change authority.
5. **Client/employer/third-party projects remain isolated.** Do not add portfolio branding, central dependencies, telemetry, cross-repo code, or changes to client repositories without the relevant authorization. Known client-related repositories include YellowBlue and MegaDealsMA; Tshono is also classified as third-party/client until reviewed. This list is not exhaustive.
6. Templates, mirrors, forks and upstream software are not to be modified just to insert portfolio links. Confirm fork status and license first.
7. New repositories must be added to this register at creation/reconciliation time, with a named canonical purpose and relationship map. Periodically reconcile the GitHub inventory; do not assume this list is exhaustive of every organization, account or private workspace.
8. Public sites must not claim authorization, certification, ownership, professional licensure, customer outcomes, or commercial status without evidence.
9. Where ownership or change authority is uncertain, document the gap and stop substantive changes pending evidence.
