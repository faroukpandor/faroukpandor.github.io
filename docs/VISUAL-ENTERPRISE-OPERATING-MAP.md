# Visual Enterprise Operating Map

**Status:** Active visual communication architecture  
**Repository:** faroukpandor/faroukpandor.github.io  
**Purpose:** Help a visitor understand and route the portfolio without requiring prior knowledge of repository names.

## Core model

**WHO:** Farouk Pandor — human + commercial orchestration layer

**INPUT:** customer problem, requirement, opportunity or research question

**ROUTING:** Need → Requirement → Evidence → Capability → Destination

**DELIVERY:** Source / Resell / Broker / Refer / Build / Coordinate / Research

**OUTPUT:** Delivered outcome → evidence → learning → repeat or route

## Capability-to-destination map

| Visitor need | Primary route | Status/control |
|---|---|---|
| Product, sourcing, resale, procurement | General Dealer / commercial layer | Supplier and stock status must be verified |
| Digital workflow, website, automation | Mokoro | Scope, ownership and implementation evidence required |
| Farm, livestock, AgTech | AgriSage360 | Specialist/regulatory boundaries remain explicit |
| Research, evidence, market intelligence | Research/intelligence assets | Source hierarchy and evidence classification apply |
| Discovery, comparison, events, opportunities | EverythingCity | Information does not equal endorsement |
| Specialist local service | Provider/referral network | Provider verification and transparent referral terms required |

## Portfolio architecture rule

The personal site is a **routing and trust layer**, not a replacement for enterprise repositories.

Enterprise repositories should retain their own:
- operating logic;
- technical implementation;
- commercial records;
- compliance controls;
- evidence;
- ownership status;
- deployment instructions;
- exit/fallback path.

## Visual design doctrine

The site may be inspired by the *communication principle* behind visual storytelling tools such as Napkin AI — converting structured text into useful visual explanations — but it must remain original in:
- content;
- information architecture;
- visual language;
- implementation;
- evidence model;
- ownership controls.

No copied Napkin UI, branding, proprietary assets or generated content is required.

## Resilience

The visual map must remain understandable if:
1. an enterprise repository is unavailable;
2. a deployment provider changes;
3. an external API disappears;
4. a commercial experiment is archived;
5. a portfolio destination changes ownership/status.

Therefore the hub uses static HTML/CSS and descriptive text as the canonical fallback. Visuals improve comprehension; they do not become the sole source of truth.

## Acceptance criteria

- A new visitor can start from a problem rather than a repository name.
- Every destination has a defined purpose.
- Ownership is not implied where it is uncertain.
- Evidence claims remain distinguishable from hypotheses.
- The page works without JavaScript, a database or a paid visualisation service.
- The visual layer can be extended with SVG/static diagrams later without creating a platform dependency.
