# Farouk Pandor — Repository & Enterprise Register

Purpose: establish a conservative source of truth for repository roles, ownership evidence, enterprise assignment and portfolio boundaries.

## Operating rule
GitHub access is not the same thing as legal ownership. Repository ownership, collaborator access, fork ancestry, client control, licences, deployment accounts and commercial rights must be separately evidenced.

No fork should be detached merely because it is accessible. First verify provenance, licence, original author, dependencies, deployment, data rights, client obligations and whether the fork contains reusable Farouk-created work.

## Portfolio boundary rules
1. AnimalHealth does not become a general veterinary clinic. It provides specialist knowledge architecture, evidence and referral/escalation pathways.
2. AgriSolutions is the field layer. It captures observations, implements agricultural services and feeds structured field evidence upward.
3. AgriSage360 is the AgTech/intelligence layer and should not duplicate AnimalHealth specialist knowledge.
4. MOKORO is the orchestration/automation layer. It monitors sources, scores relevance, routes alerts and coordinates workflows.
5. PANDOR-ESTATES/Africa Realty owns the property context. Regulated services remain with appropriately qualified providers.
6. Client repositories remain client-controlled. Access or contribution does not turn client IP into Farouk-owned IP.
7. Forks require provenance review before detachment.

## Minimum evidence register
For every important repository record: GitHub owner; authenticated access level; fork status/upstream; original author/provenance; licence; major dependencies; deployment URL/account; domain owner; data ownership; client/third-party obligations; canonical enterprise; lifecycle status; commercial purpose; next action.

## Decision vocabulary
ACTIVE-CANONICAL — primary repository for an enterprise function.
ACTIVE-SUPPORTING — useful dependency or supporting asset.
CONSOLIDATE — retain useful IP but stop adding overlapping features.
PROVENANCE-REVIEW — ownership/licence/authorship/deployment needs evidence.
CLIENT-CONTROLLED — do not modify without authorization.
ARCHIVE — preserve for historical/reference value.

## Critical conclusion
The portfolio should not be judged by repository count. It should be judged by whether each repository has one defensible customer problem, one accountable enterprise role, clear IP provenance, evidence-backed claims and a credible route to value and revenue.
